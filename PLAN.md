# Проект: Syncthing Event-Driven Music Tagger

**Theme:** Автоматизація, ідентифікація та впорядкування музичної бібліотеки за допомогою Event-Driven архітектури та спеціалізованого Sidecar-контейнера.

---

## Epic 1: Інфраструктура та Конфігурація (Infrastructure as Code)
**Мета:** Підготувати середовище для запуску компонентів, забезпечити їх мережеву взаємодію та управління конфігураціями згідно з принципами 12-Factor App.

* **User Story 1.1:** Як DevOps інженер, я хочу розгорнути систему через Docker Compose, щоб забезпечити ізоляцію сервісів, спільну мережу та дисковий простір.
    * *Task 1.1.1:* Створити `docker-compose.yml` з декларацією сервісів `syncthing` та `music-tagger`.
    * *Task 1.1.2:* Налаштувати спільний volume `/music` та volume для конфігів `/config`.
    * *Task 1.1.3:* Написати базовий `Dockerfile` для `music-tagger` (на базі офіційного образу Python 3.13+).
* **User Story 1.2:** Як адміністратор безпеки, я хочу передавати конфігурацію та токени виключно через змінні оточення.
    * *Task 1.2.1:* Створити файл `.env.example` з декларацією `SYNCTHING_API_KEY`, `SYNCTHING_URL`, та `OTEL_EXPORTER_OTLP_ENDPOINT`.
    * *Task 1.2.2:* Написати `docker-entrypoint.sh` для `music-tagger`, який генеруватиме базовий `config.yaml` для Beets з шаблону, якщо він відсутній на змонтованому диску.

## Epic 2: Event-Driven Рушій (Python Poller)
**Мета:** Навчити Sidecar-контейнер слухати події від Syncthing і відсікати системне сміття.

* **User Story 2.1:** Як система, я маю постійно слухати API Syncthing, щоб миттєво реагувати на завантаження нових файлів.
    * *Task 2.1.1:* Розробити модуль `syncthing_client.py` для виконання long-polling HTTP запитів до `/rest/events`.
    * *Task 2.1.2:* Додати обробку таймаутів та автоматичне перепідключення (Retry-Backoff).
    * *Task 2.1.3:* Реалізувати збереження `last_seen_id` (у пам'яті або локальному tmp-файлі), щоб не обробляти старі події після рестарту контейнера.
* **User Story 2.2:** Як система, я маю фільтрувати події, щоб запускати важкий процес розпізнавання тільки для релевантних файлів.
    * *Task 2.2.1:* Створити модуль `router.py`, який відфільтровує події за умовами `action == 'update'` та `type == 'file'`.
    * *Task 2.2.2:* Написати фільтри відкидання шляхів, що містять `.tmp`, `sync-conflict`, або починаються з `/_unsorted/`.

## Epic 3: Ідемпотентність та Пайплайн Beets
**Мета:** Запобігти нескінченним циклам обробки (DRY) та реалізувати логіку перейменування/переміщення файлів.

* **User Story 3.1:** Як система, я маю перевіряти стан файлу за його метаданими, щоб зрозуміти, чи він вже був оброблений.
    * *Task 3.1.1:* Встановити бібліотеку `mutagen` та розробити модуль `inspector.py`.
    * *Task 3.1.2:* Реалізувати читання ID3 (для MP3), тегів для AAC та Vorbis/FLAC тегів для пошуку наявності `MusicBrainz Track Id`.
* **User Story 3.2:** Як користувач, я хочу, щоб розпізнана музика перейменовувалась, але залишалась у своїй поточній підпапці.
    * *Task 3.2.1:* Створити шаблон `beets_default.yaml`, що використовує `inline` плагін для обчислення `$current_dir` та форматує ім'я як `%artist% - %title%`.
    * *Task 3.2.2:* Написати модуль `processor.py`, який формує і викликає команду `subprocess.run(['beet', 'import', '-q', ...])`.
* **User Story 3.3:** Як користувач, я хочу мати надійний фолбек для нерозпізнаних файлів (перенесення у `_unsorted`).
    * *Task 3.3.1:* Розробити логіку перевірки результату виконання Beets.
    * *Task 3.3.2:* Якщо Beets не розпізнав файл: додати функцію зчитування існуючих тегів `Artist` та `Title` через `mutagen`.
    * *Task 3.3.3:* Якщо теги є — перейменувати файл відповідно, якщо ні — залишити як є. В обох випадках перемістити файл до `/music/_unsorted/`.

## Epic 4: Observability (OpenTelemetry)
**Мета:** Забезпечити прозорість роботи системи через збір метрик та розподілених трейсів для легкого дебагу і моніторингу.

* **User Story 4.1:** Як SRE, я хочу збирати базові метрики обробки файлів.
    * *Task 4.1.1:* Інтегрувати `opentelemetry-metrics` SDK у Python демон.
    * *Task 4.1.2:* Створити лічильник `processed_files_total` з лейблом `status` (`sorted` або `unsorted`).
    * *Task 4.1.3:* Експонувати Prometheus HTTP endpoint на порту `8000`.
* **User Story 4.2:** Як SRE, я хочу мати розподілене трасування (Tracing) всього життєвого циклу обробки файлу.
    * *Task 4.2.1:* Налаштувати `OTLPSpanExporter` для відправки трейсів у Grafana Alloy.
    * *Task 4.2.2:* Огорнути основні етапи (listen, guard_filters, idempotency_check, beets_processing) у відповідні Spans.
    * *Task 4.2.3:* Забезпечити дублювання структурованих логів у `stdout`.
* **User Story 4.3:** Як інженер з моніторингу, я хочу підключити Grafana Alloy до цього сервісу.
    * *Task 4.3.1:* Написати базовий конфіг `alloy.river` для: 1) scrape метрик з порту 8000; 2) прийому OTLP трейсів/логів на порту 4317.
